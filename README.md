# Event LED Pose

Low-latency frequency-based detection of a rigid three-LED marker using a Prophesee EVK4 / Sony IMX636 event camera.

Each LED flashes at a different nominal frequency:

| LED ID    | Frequency | Display color |
| --------- | --------: | ------------- |
| `led_165` |    165 Hz | Green         |
| `led_366` |    366 Hz | Yellow        |
| `led_596` |    596 Hz | Blue          |

The current implementation is C++ only and focuses on low-latency event-by-event frequency filtering using event polarity and per-pixel timestamp history.

Metric 6-DoF pose estimation is not implemented yet.

## Current scope

The current C++ pipeline:

- reads events directly from the EVK4;
- keeps separate positive- and negative-polarity timestamp histories per pixel;
- suppresses very short event bursts;
- checks timestamps against the known LED periods;
- allows missed LED transitions through integer period multiples;
- uses opposite-polarity timing as additional frequency evidence;
- visualizes accepted events in real time;
- avoids building a queue of old visualization frames.

## Frequency-filter design

Each pixel keeps separate timestamp histories for positive and negative events.

For a candidate LED frequency f the expected period is T = 1 / f. Same-polarity events are expected near integer period multiples: T, 2T, 3T, ...

This allows a pixel to miss one or more LED transitions without immediately losing the frequency hypothesis.

Opposite-polarity timing is used as additional evidence when available, but both polarities are not required because a pixel may miss one transition polarity.

The filter also suppresses very short event bursts so that several events generated by one physical transition are not incorrectly treated as several independent frequency observations.

## Low-latency design

The project is intended to remain event-driven and avoid frame reconstruction for frequency detection.

Important design goals are:

- event-by-event processing;
- bounded per-pixel memory;
- no historical visualization queue;
- no FFT in the live frequency filter;
- no dynamic allocation in the per-event hot path;
- separate acquisition/filtering and visualization behavior where possible.

The display should always prefer the newest available filtered events rather than replaying stale data.

## Current limitations

- The frequency classifier can still produce false positives on moving background edges.
- Frequency discrimination depends on timestamp-history length and timing tolerance.
- A single pixel may miss one or both polarity transitions.
- Spatial LED center extraction and rigid-marker pose estimation are still under development.
- Metric 6-DoF pose is not yet implemented.
- The current implementation is optimized for known LED frequencies rather than arbitrary frequency estimation.

## Next steps

Current development priorities:

1. reduce false frequency detections from fast moving background edges;
2. improve temporal coherence checks while keeping per-pixel state small;
3. benchmark event throughput and end-to-end latency;
4. separate frequency identity from instantaneous LED position;
5. estimate stable LED centers;
6. add rigid three-point marker tracking;
7. add calibrated 6-DoF pose estimation;
8. remove the container dependency once the native OpenEB setup is reproducible.
